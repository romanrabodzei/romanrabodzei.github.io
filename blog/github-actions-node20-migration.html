GitHub Actions After Node 20: Migration & Security Checklist

Roman Rabodzei · Oct 2026 · ~7 min read
GitHub Actions CI/CD DevOps Migration

Node 20 stopped being available in GitHub Actions on September 23, 2026. If any workflow, composite action, or self-hosted runner in your pipelines still depends on it directly or indirectly, this is the point where things silently start failing rather than just showing a deprecation warning. This post is the checklist I ran across our own pipelines this week, and what I'd recommend running against yours.

Why this retirement is easy to miss

Runtime retirements in Actions rarely fail loudly in one place. The actual runtime for JavaScript-based actions is often pinned deep inside a third-party action's action.yml, not something visible in your own workflow file. A workflow that looks completely unrelated to Node.js can still break because one of its steps uses an older major version of a popular action (checkout, setup-*, upload-artifact) that hasn't been updated to declare a supported runtime.

The audit checklist

  1. Grep every workflow file for pinned action versions. Anything on @v3 or older for common actions (checkout, setup-node, setup-python, upload-artifact, download-artifact) is worth checking against the action's changelog for its Node runtime requirement.
  2. Check custom composite and JavaScript actions your org maintains. Any action.yml with using: node20 needs to be updated to node22 or later — this is the one teams most often forget because it's their own code, not a dependency.
  3. Review self-hosted runner images. If you maintain your own runner images (rather than using GitHub-hosted runners), confirm the pre-installed Node.js version on the image matches what current actions expect.
  4. Re-run workflows in a dry-run or feature branch before assuming production pipelines are unaffected — some failures only surface under specific trigger conditions (scheduled runs, matrix builds) that don't get exercised on every push.
  5. Check third-party marketplace actions you depend on that haven't been updated in over a year — these are the highest-risk dependencies, since an unmaintained action pinned to Node 20 simply stops working with no upstream fix coming.

Fastest way to find the risk surface: search your workflows directory for uses: lines, extract the unique set of actions and pinned versions, and cross-reference against each action's repository for its current supported runtime. For an organisation with many repositories, this is worth scripting once and running as a scheduled check rather than doing manually per-repo.

Beyond this migration: pin by SHA, not just by tag

While auditing action versions, it's worth taking the opportunity to move from version-tag pinning (@v4) to commit-SHA pinning for any action you can't fully vet — tags can be moved, SHAs can't. This retirement is a good forcing function to combine a runtime migration with a supply-chain hardening pass on the same set of workflows, rather than treating them as two separate projects.

My take

Runtime retirements in GitHub Actions are announced well in advance, but the actual failure mode when the retirement date arrives is abrupt rather than gradual — a step either works or it doesn't. Treat every Actions runtime deprecation notice as a trigger to run a full dependency audit across your workflows, not just a note to update one pipeline you remember using an old action.
