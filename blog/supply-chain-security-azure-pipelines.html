Supply Chain Security in Azure Pipelines: SBOM, Cosign, and Ratify on AKS

Roman Rabodzei · Aug 2026 · ~10 min read
Azure DevOps Security SBOM Cosign ACR DevSecOps Supply Chain

Software supply chain attacks have moved from theoretical concern to operational reality. The incidents that made headlines — SolarWinds, the xz backdoor, repeated compromised base images — share a common thread: the attack happened below the application layer, in the dependencies and build artifacts that teams implicitly trust. The response from the industry has converged on a few concrete tools and practices: software bills of materials (SBOMs), cryptographic image signing, and admission-time verification. This post walks through wiring all three into Azure Pipelines with Azure Container Registry and Ratify on AKS.

The threat model and what we're actually defending against

Before adding security tooling, it's worth being precise about what it protects. The supply chain threat model has three main attack surfaces:

  • Compromised dependencies: a package you depend on is tampered with upstream. An SBOM lets you inventory what's in your image and cross-reference against vulnerability feeds or known-compromised package versions.
  • Tampered build artifacts: an image in your registry is replaced or modified after it was built and tested. A cryptographic signature on the image digest lets you detect this at deploy time.
  • Unauthorised images: a workload is deployed from an image that was never built by your CI pipeline. Admission-time signature verification enforces that only pipeline-signed images run in your cluster.

None of these controls are a silver bullet. They don't prevent a vulnerability in your application code, and they don't protect against a compromised CI environment with signing keys. But together they close the most common attack paths and give you the audit trail to detect and respond when something does go wrong.

SLSA: a framework for placing where you are

The Supply-chain Levels for Software Artifacts (SLSA) framework gives a structured vocabulary for supply chain security maturity. The levels relevant to a typical Azure DevOps / AKS setup are:

  • SLSA Level 1: provenance exists — the build system generates a record of how the artifact was produced. An SBOM stored alongside the image satisfies the basic provenance requirement.
  • SLSA Level 2: provenance is signed — the build system cryptographically signs the provenance. Cosign signing with an OIDC-based identity (your Azure DevOps service connection or managed identity) satisfies this.
  • SLSA Level 3: the build is hardened — the build environment itself is tamper-resistant, the provenance is non-forgeable, and the signing identity is tied to the specific pipeline run. Keyless Cosign signing with short-lived OIDC tokens from the pipeline identity, stored as OCI attestations in ACR, gets you to Level 3 for the provenance piece.

Most teams starting out should target Level 2 as the initial goal. It's achievable in a single sprint and closes the most common attack paths. Level 3 hardening requires additional investment in build environment isolation that's worth planning separately.

Generating SBOMs with Syft in Azure Pipelines

Syft from Anchore is the most practical SBOM generator for container images in a CI pipeline. It supports SPDX and CycloneDX output formats, runs as a single binary with no daemon, and can scan an image from a local docker daemon or a registry reference.

Add it as a step after your image build, before the push: 

- task: Bash@3
  displayName: 'Install Syft'
  inputs:
    targetType: inline
    script: curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh | sh -s -- -b /usr/local/bin

- task: Bash@3
  displayName: 'Generate SBOM (SPDX)'
  inputs:
    targetType: inline
    script: |
      syft $(IMAGE_TAG) \
        -o spdx-json \
        --file sbom.spdx.json

The output file sbom.spdx.json is the artifact you'll attach to the image as an OCI attestation in the next step. Store it as a pipeline artifact for audit purposes as well — having an out-of-band copy in Azure Artifacts means you can reconstruct what was in an image even if the ACR attestation is somehow lost.

On SBOM completeness: Syft's analysis is best-effort for dynamically linked dependencies and anything installed via custom scripts in your Dockerfile. Treat the SBOM as a strong approximation, not an exhaustive inventory — and schedule regular re-scans against updated vulnerability databases, not just at build time.

Signing images with Cosign

Cosign from Sigstore handles image signing and attestation storage. The most robust approach on Azure is keyless signing: rather than managing a long-lived signing key, Cosign uses an OIDC token from your pipeline identity to request a short-lived certificate from Sigstore's Fulcio CA. The certificate binds the signature to the pipeline run identity, and the certificate issuance is recorded in Sigstore's Rekor transparency log.

For Azure DevOps, the pipeline identity is your service connection's managed identity. Configure Cosign to use it: 

- task: Bash@3
  displayName: 'Install Cosign'
  inputs:
    targetType: inline
    script: |
      curl -sSfL https://github.com/sigstore/cosign/releases/latest/download/cosign-linux-amd64 \
        -o /usr/local/bin/cosign && chmod +x /usr/local/bin/cosign

- task: AzureCLI@2
  displayName: 'Sign image and attach SBOM attestation'
  inputs:
    azureSubscription: $(SERVICE_CONNECTION)
    scriptType: bash
    scriptLocation: inlineScript
    inlineScript: |
      # ACR login via managed identity
      az acr login --name $(ACR_NAME)

      # Sign the image (keyless, OIDC via Azure AD)
      COSIGN_EXPERIMENTAL=1 cosign sign \
        --yes \
        $(ACR_LOGIN_SERVER)/$(IMAGE_NAME)@$(IMAGE_DIGEST)

      # Attach SBOM as an OCI attestation
      COSIGN_EXPERIMENTAL=1 cosign attest \
        --yes \
        --predicate sbom.spdx.json \
        --type spdxjson \
        $(ACR_LOGIN_SERVER)/$(IMAGE_NAME)@$(IMAGE_DIGEST)

A few important details here. Sign the image by digest, not by tag. Tags are mutable — signing a tag gives you a signature on whatever the tag pointed to at signing time, which is not what you want. The digest is immutable and uniquely identifies the image layers. You can get the digest from the docker push output or by running docker inspect --format='{{index .RepoDigests 0}}' <image>.

Signatures and attestations are stored in ACR as separate OCI objects linked to the signed image. They're retained as long as the image is retained, and they don't affect the image pull behaviour for existing clients — verification is opt-in until you enforce it at admission.

Enforcing verification at admission with Ratify

Ratify is a CNCF project that integrates with the Gatekeeper OPA admission controller to verify OCI artifacts — signatures, SBOMs, vulnerability scan results — before a pod is admitted to the cluster. On AKS, it works with Azure Policy's built-in Kubernetes integration.

Install Ratify via Helm and configure it with a Store pointing at your ACR using workload identity (the right approach — avoid static credentials): 

apiVersion: config.ratify.deislabs.io/v1beta1
kind: Store
metadata:
  name: store-oras
spec:
  name: oras
  parameters:
    authProvider:
      name: azureWorkloadIdentity
      clientID: $(RATIFY_CLIENT_ID)
---
apiVersion: config.ratify.deislabs.io/v1beta1
kind: Verifier
metadata:
  name: verifier-cosign
spec:
  name: cosign
  artifactTypes: application/vnd.dev.cosign.artifact.sig.v1+json
  parameters:
    key: https://fulcio.sigstore.dev  # keyless: validates against Fulcio root

With Ratify installed, apply an Azure Policy assignment that enforces the Kubernetes cluster containers should only use allowed images built-in with a Ratify-backed constraint template. Any pod attempting to use an unsigned or unattested image will be rejected at admission — not at runtime — with a clear policy violation message.

// start in audit mode

Before enforcing, run Ratify in audit mode for at least one release cycle. Audit mode reports violations without blocking deployments. Use this period to catch any legitimate images (infrastructure components, third-party operators) that pull from registries or use digests that won't pass Cosign verification, and decide whether to add exceptions or migrate those images into your signing pipeline.

Putting it together: the full pipeline sequence

The complete sequence in an Azure Pipeline, in order:

  1. Build the container image from source.
  2. Push the image to ACR and capture the digest from the push output.
  3. Run Syft against the image to generate an SPDX SBOM.
  4. Sign the image digest with Cosign using the pipeline's managed identity (keyless).
  5. Attach the SBOM as a Cosign attestation against the same digest.
  6. Store the SBOM as a pipeline artifact for out-of-band audit.
  7. At deploy time, Ratify verifies the signature and attestation before AKS admits the pod.

The incremental cost of this sequence is low — Syft and Cosign are fast single-binary tools that add roughly 30–60 seconds to a typical build pipeline. The operational overhead post-setup is minimal: once Ratify is in enforce mode, unsigned images simply don't run, and the failure message tells you exactly why.

What this doesn't solve

It's worth being direct about the limits. This setup gives you strong guarantees that what runs in your cluster was built by your CI pipeline and hasn't been tampered with since. It does not give you:

  • A guarantee that the code in the image is free of vulnerabilities. An SBOM enables you to check against CVE databases, but you need to integrate that check separately (Trivy, Grype, Microsoft Defender for Containers).
  • Protection against a compromised pipeline. If an attacker can modify your pipeline YAML or the build agent, they can sign malicious images legitimately. This is why pipeline-as-code review and branch protection matter as much as the signing itself.
  • Supply chain security for your base images. If you pull ubuntu:24.04 and it's compromised upstream, Cosign signing your layer on top of it doesn't help. Using ACR's image import feature to pull base images through your registry, scanning them on import, and signing them yourself closes this gap.

Supply chain security is a posture you improve over time, not a binary you flip on. Getting SBOM generation and signature enforcement in place is the right first step — it establishes the audit trail and the enforcement point that everything else builds on.
