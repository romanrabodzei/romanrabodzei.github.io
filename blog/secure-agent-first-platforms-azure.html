Designing Secure Agent-First Platforms on Azure: Five Layers Before You Trust an Agent

Roman Rabodzei · Oct 2026 · ~9 min read
Microsoft Foundry AI Agents Security Agent 365 Platform Engineering

Every serious conversation I've had this quarter about AI agents on Azure eventually turns into a security conversation. That's the right instinct. Azure's own messaging shifted noticeably in September 2026 toward the idea that agents don't just think, they act — and anything that acts needs to be secured before it acts, not audited afterward. This post is my attempt to turn that into a concrete platform design, using what's actually shipped: network egress controls for hosted agents, Agent 365 governance controls, and Foundry Routines.

Start from the assumption that agents will misbehave

The useful mental model for agent-first platform security isn't "how do we stop a malicious actor from misusing this agent" — it's "what happens when this agent, doing exactly what it was designed to do, takes an action nobody anticipated." Agents chain tool calls, retrieve data, and sometimes execute generated code. Each of those is an action with real consequences if scoped too broadly, regardless of whether the model itself was compromised.

That reframing changes what you build first. Instead of starting with content filtering and prompt injection defence (both still necessary), start with the blast radius question: if this agent does something wrong, what can it actually reach, and how quickly can that be revoked?

Layer one: identity, not shared credentials

Every agent instance should have its own identity — not a shared service principal reused across every agent in a project. This is the same principle as workload identity for microservices, applied to agents: scoped permissions, auditable actions attributable to a specific agent instance, and the ability to revoke one agent's access without affecting others. If your current agent deployment shares a single managed identity across every agent in a Foundry project, that's the first thing to fix.

Layer two: network egress controls

Network egress controls for hosted agents in Microsoft Foundry — in preview through mid-2026 — let you constrain exactly what network destinations an agent's runtime can reach. This matters enormously for agents that execute generated code or call external tools: without egress control, a compromised or misdirected agent can exfiltrate data to any reachable endpoint. With it, you define an allow-list of destinations the agent's runtime is permitted to reach at all, and everything else is blocked at the network layer regardless of what the agent's logic tries to do.

This is the layer I'd prioritise before anything else if you're deploying agents that touch sensitive data. Application-level guardrails can be bypassed by a sufficiently unexpected model output; a network boundary enforced outside the agent's own control cannot.

Layer three: isolated execution for generated code

For agents that write and run code — increasingly common for data transformation and analysis tasks — the execution boundary matters as much as the network boundary. Azure Container Apps Sandboxes (covered in my previous post) is the natural fit here: fast-starting, strongly isolated execution contexts purpose-built for untrusted code, callable directly from a Foundry agent's tool definitions. Don't run agent-generated code in the same execution context as your orchestration logic — that collapses two boundaries that should stay separate.

Layer four: Agent 365 governance

Agent 365's enable/disable controls, reaching GA in August 2026, give platform teams an organisation-wide kill switch and lifecycle management layer for Foundry agents — the ability to see what agents exist, who owns them, and disable one immediately without redeploying anything. This is the layer that turns "we have agents running somewhere" into an actual managed inventory, the same shift identity governance went through for human accounts a decade ago.

A gap I still see often: teams treat agent governance as a launch-day checkbox rather than an ongoing inventory discipline. Agents get created for a pilot, the pilot ends, and the agent — with its identity, permissions, and tool access — quietly keeps running. Agent 365's governance controls are only as good as the process that reviews the inventory regularly.

Layer five: Foundry Routines for predictable behaviour

Foundry Routines, in preview since mid-2026, let you define structured, constrained execution paths for an agent rather than leaving every decision to free-form model reasoning. For high-stakes or compliance-sensitive workflows, this is a meaningful security control in its own right: a routine limits what the agent can do at each step, which reduces the surface area an attacker (or a confused model) has to work with in the first place.

Putting it together

A secure agent-first platform on Azure, as of this writing, looks like: scoped per-agent identity, network egress allow-listing at the runtime layer, isolated sandboxes for any generated-code execution, an organisation-wide governance inventory through Agent 365, and structured Routines constraining behaviour for the workflows where predictability matters most. None of these pieces is optional if you're running agents against production data — they're complementary layers, not alternatives to each other.
