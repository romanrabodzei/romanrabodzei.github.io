The C.R.A.F.T. Framework: A Prompt Structure That Actually Holds Up

Roman Rabodzei · Oct 2026 · ~7 min read
Prompt Engineering AI Productivity GitHub Copilot DevOps LLMs

I've watched a lot of smart engineers type a one-line request into Copilot or ChatGPT, get something mediocre back, and conclude "the model isn't that good for this." Nine times out of ten the model was fine. The prompt was missing most of the information a competent human would have needed to do the task too. If you asked a contractor to "build me a deck" with no dimensions, no material preference, and no budget, you wouldn't blame the contractor for guessing wrong.

The C.R.A.F.T. framework — Context, Role, Action, Format, Tone — is the simplest fix I've found for this. It's not clever. That's the point. It's a checklist you can run through in ten seconds before you hit enter, and it catches almost every prompt failure I see on a daily basis.

Why "just ask better" isn't advice

"Write better prompts" is not actionable — it's the same category of advice as "write better code." What actually helps is a structure you can apply mechanically, every time, without having to be inspired. C.R.A.F.T. gives you five slots to fill. If you can't fill one of them, that's useful information too — it usually means you don't actually know what you want yet, and the model doesn't stand a chance of guessing it for you.

The five letters

// Context

What does the model need to know that it can't infer? This is almost always the most skipped part. The model doesn't know your stack, your constraints, your audience, or what "done" looks like for you specifically. A request like "create a CI/CD pipeline" has no context — the model has to guess at the language, the platform, the deployment target, and your team's conventions, and it will guess based on the most common answer on the internet, which is very often not your answer.

// Role

Telling the model who it should act as narrows the space of plausible responses. "You are a senior SRE who's been paged at 3 AM" produces a terser, more action-oriented answer than no role at all. The useful roles are specific enough to imply constraints, not just vibes — "a security reviewer with a checklist" beats "a security expert," because a checklist implies the model should stick to known criteria instead of improvising.

// Action

This is the actual task, stated as one unambiguous instruction — not a vague direction. "Help me with my deployment" is not an action. "Write a GitHub Actions workflow that builds a container image, scans it for CVEs, and blocks the push on any critical finding" is an action. If you can't state the action in one sentence without an "and also," you probably have two tasks, not one — split the prompt.

// Format

What shape does the output need to take, and what will you do with it immediately after? If you're going to paste the output into a YAML file, ask for YAML and nothing else — not "here's your pipeline" followed by a code block followed by three paragraphs of explanation you'll delete anyway. Be explicit: "respond with only the YAML, no prose before or after it." Models default to being helpful with commentary unless you tell them not to be.

// Tone

The one people skip because it feels like the least important letter — but tone shapes how much you'll trust and actually use the output. A runbook written for a junior on-call engineer needs a different tone than an architecture decision record for a staff engineering review. If you don't specify, you get a generic, slightly over-explained middle-ground tone that satisfies nobody particularly well.

The fastest way to tell a prompt is missing a pillar: read it out loud and ask "would a smart colleague with zero context about my project know exactly what to hand back to me?" If the honest answer is no, find out which letter is missing and add it. It's almost always Context or Format.

Create a CI/CD pipeline

C.R.A.F.T.:

  • Context: Node.js application, deployed to AWS ECS, using GitLab CI.
  • Role: Act as a senior DevOps engineer who favours boring, reliable pipelines over clever ones.
  • Action: Create a GitLab CI/CD pipeline that runs security scanning and automated tests, then performs a blue-green deployment to ECS.
  • Format: A single .gitlab-ci.yml file, fully commented, no explanation before or after.
  • Tone: Production-ready — include error handling and a rollback job, don't simplify for readability.

Same request, five extra sentences, and the difference in output quality isn't incremental — it's the difference between something you can actually merge and something you have to rewrite from scratch.

Where C.R.A.F.T. and "proper" prompt engineering agree

If you've read more rigorous prompt engineering material, you'll recognise the overlap: Context and Role map directly onto the same ideas, Action is just "task" by another name, and Format is the same non-negotiable most production systems enforce with schema-constrained output rather than just asking nicely. Tone is the one addition that's more about human-facing prompts than machine-to-machine ones — when the output is JSON consumed by code, tone mostly doesn't matter; when a person is going to read the result, it matters a lot.

The deeper lesson both approaches share: a prompt that works reliably is not a clever sentence, it's a small, complete specification. Missing any one piece turns a specification into a guess, and guesses are exactly as reliable as you'd expect.

A habit worth building

I keep a scratch note with the five letters next to my editor. Before sending any non-trivial prompt, I run down the list: do I know the context, have I given it a role, is the action one unambiguous sentence, have I said what shape I want back, and have I set the tone for who's going to read it? It takes ten seconds and it's the single highest-leverage habit I've picked up for working with AI tools day to day — far more useful than any individual "magic prompt" I've collected.
