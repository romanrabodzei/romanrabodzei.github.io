GitOps for Azure Infrastructure with Crossplane on AKS: Providers, Compositions, and Drift Correction

Roman Rabodzei · Sep 2026 · ~12 min read
Kubernetes Azure GitOps Crossplane Infrastructure as Code AKS Flux

There's a gap in most GitOps setups. Application workloads — Deployments, Services, ConfigMaps — are reconciled continuously from Git via Flux or ArgoCD. But the Azure infrastructure those workloads depend on — the storage accounts, message queues, databases, and Key Vaults — is managed separately: Terraform state in a pipeline, Bicep deployed on merge to main, or worse, click-ops that was never captured anywhere. The two halves of the system operate under fundamentally different operational models, with different audit trails, different drift detection postures, and different blast radius when something goes wrong.

Crossplane closes this gap. It's a CNCF graduated project that runs inside your Kubernetes cluster and manages cloud infrastructure through the same Kubernetes control loop that manages your pods — desired state declared in YAML, continuously reconciled, drift automatically corrected. If you already have GitOps working for your workloads, Crossplane extends that same model all the way down to the cloud layer.

How Crossplane works

Crossplane introduces a few abstractions worth understanding before looking at configuration:

  • Providers: Crossplane plugins that know how to talk to a specific cloud API. provider-azure-upbound is the official Microsoft-maintained provider. Installing it installs hundreds of Azure-specific CRDs — one per Azure resource type — into your cluster.
  • Managed Resources: individual CRD instances that represent a single Azure resource. A storage.azure.upbound.io/v1beta1 Account maps to an Azure Storage Account. Crossplane reconciles managed resources against Azure ARM continuously.
  • Composite Resources (XRDs and Compositions): the abstraction layer that lets you define reusable infra patterns. An XRD (Composite Resource Definition) declares a new custom API surface — say, XDataPlatform — and a Composition maps that to the specific managed resources it comprises. Consumers reference the composite, not the individual resources.
  • ProviderConfig: the authentication and scope configuration for the provider. On AKS, this should use Workload Identity — a managed identity with the right RBAC roles, bound to the Crossplane provider service account via federated credential.

The reconciliation model is identical to how Kubernetes manages pods. Crossplane reads the desired state from your managed resource spec, calls Azure ARM to observe the actual state, diffs them, and issues create/update/delete calls to converge. Drift — someone manually changed a setting in the Azure portal, or a Terraform run partially failed — is detected on the next reconcile cycle and corrected automatically unless you explicitly annotate the resource to suspend reconciliation.

Setting up the provider with Workload Identity

The first decision is authentication. The Azure provider needs permissions to create and manage resources in your subscription. The right approach on AKS is Workload Identity — no client secrets, no certificates to rotate, no credentials in Kubernetes secrets.

Create a managed identity, assign the roles it needs (at minimum Contributor on the target resource group, User Access Administrator if Crossplane needs to assign RBAC roles to managed resources), and add a federated credential that trusts the Crossplane provider service account: 

# assign roles to the managed identity
az role assignment create \
  --assignee $CROSSPLANE_CLIENT_ID \
  --role Contributor \
  --scope /subscriptions/$SUBSCRIPTION_ID/resourceGroups/$RESOURCE_GROUP

# federated credential: trust the provider service account
az identity federated-credential create \
  --name crossplane-provider-azure \
  --identity-name crossplane-mi \
  --resource-group $RESOURCE_GROUP \
  --issuer $AKS_OIDC_ISSUER \
  --subject "system:serviceaccount:crossplane-system:provider-azure-upbound" \
  --audience api://AzureADTokenExchange

Then configure the provider to use it: 

apiVersion: azure.upbound.io/v1beta1
kind: ProviderConfig
metadata:
  name: default
spec:
  credentials:
    source: OIDCTokenFile
    oidcTokenFilePath: /var/run/secrets/azure/tokens/azure-identity-token
  clientID: $(CROSSPLANE_CLIENT_ID)
  subscriptionID: $(AZURE_SUBSCRIPTION_ID)
  tenantID: $(AZURE_TENANT_ID)

Managed resources: declaring Azure infrastructure as YAML

With the provider configured, you can start declaring Azure resources as Kubernetes manifests. Here's a Storage Account with hierarchical namespace enabled (Data Lake Gen2) and ZRS replication: 

apiVersion: storage.azure.upbound.io/v1beta2
kind: Account
metadata:
  name: datalake-prod
  annotations:
    crossplane.io/external-name: stproddatalake001  # actual Azure resource name
spec:
  forProvider:
    resourceGroupName: rg-data-prod
    location: eastus2
    accountTier: Standard
    accountReplicationType: ZRS
    isHnsEnabled: true              # Data Lake Gen2
    minTlsVersion: TLS1_2
    allowBlobPublicAccess: false
    tags:
      environment: production
      managed-by: crossplane
  providerConfigRef:
    name: default

Apply this manifest and Crossplane creates the storage account in Azure. Modify the manifest (change replication type, update a tag) and commit it to Git — Flux syncs it to the cluster, Crossplane reconciles the change to Azure. Delete the manifest and Crossplane deletes the resource (unless you set a deletionPolicy: Orphan annotation to retain it on manifest removal).

On deletion policy: the default is Delete — removing the Kubernetes manifest deletes the Azure resource. For production stateful resources (databases, storage with data), always set crossplane.io/paused: "true" or deletionPolicy: Orphan on first creation, and remove it only after verifying your team understands the deletion behaviour. A misconfigured GitOps automation deleting a production database is an unpleasant experience.

Composite Resources: reusable infra patterns

Managed resources are powerful but verbose. If every team that needs a "standard data platform environment" has to declare individual Storage Accounts, Service Bus namespaces, and Key Vaults from scratch, you get inconsistency and configuration drift across environments. Composite Resources solve this with a platform engineering model: the platform team defines and owns the composition; application teams consume a higher-level API.

An XRD defines the API surface: 

apiVersion: apiextensions.crossplane.io/v1
kind: CompositeResourceDefinition
metadata:
  name: xdataplatforms.infra.example.com
spec:
  group: infra.example.com
  names:
    kind: XDataPlatform
    plural: xdataplatforms
  versions:
    - name: v1alpha1
      served: true
      referenceable: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                environment:
                  type: string
                  enum: [dev, staging, production]
                location:
                  type: string

A Composition maps XDataPlatform to the actual managed resources — a Storage Account, Service Bus namespace, and Key Vault wired together with consistent naming conventions and tags derived from the composite's parameters. Application teams then only need to declare: 

apiVersion: infra.example.com/v1alpha1
kind: XDataPlatform
metadata:
  name: team-alpha-data
spec:
  environment: production
  location: eastus2

The composition handles the rest. Changes to the composition template propagate to all composite instances on the next reconcile — the platform team can update a tagging standard or add a new security control and have it applied consistently across every instance without touching individual team manifests.

Flux integration: closing the GitOps loop

Crossplane manages the reconciliation between Kubernetes and Azure. Flux manages the reconciliation between Git and Kubernetes. Together they form a complete GitOps loop: commit a manifest to Git, Flux syncs it to the cluster, Crossplane reconciles the Azure resource.

The Flux configuration for Crossplane infrastructure is straightforward. A GitRepository pointing at your infra repo, and a Kustomization targeting the infrastructure manifests path, with dependencies declared explicitly: 

apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: crossplane-infra
  namespace: flux-system
spec:
  interval: 5m
  sourceRef:
    kind: GitRepository
    name: infra-repo
  path: ./infra/azure
  prune: true         # deletions in Git propagate to cluster (and then to Azure)
  dependsOn:
    - name: crossplane-providers   # providers must be healthy before infra manifests

The prune: true setting means that deleting a manifest from Git will delete the Kubernetes object, which will trigger Crossplane to delete the Azure resource (subject to deletion policy). This is powerful — and requires the same care around branch protection and PR review that you'd apply to any IaC change that can delete production resources.

State management and what happens when things drift

Crossplane doesn't use Terraform state files. The Kubernetes etcd store is the state database — managed resource objects contain the last observed state from Azure in their status field. This means there's no state lock contention, no remote state backends to manage, and no state drift between a pipeline run and what's actually in Azure.

When Azure resource state drifts from the spec — an engineer manually changed a setting in the portal, or an Azure policy assignment modified a property — Crossplane detects it on the next observe cycle (default: 10 minutes, configurable) and issues an update to restore the declared spec. The drift event is visible in kubectl describe on the managed resource object and in Kubernetes events, and you can alert on it via Prometheus if you instrument the Crossplane metrics endpoint.

To intentionally pause reconciliation on a resource (during a migration, or while investigating an Azure-side change), annotate it with crossplane.io/paused: "true". Crossplane will stop reconciling that resource until you remove the annotation. This is the escape hatch for operational situations where the GitOps loop needs to be temporarily overridden.

Crossplane vs Terraform: not a binary choice

The honest answer to "should I replace Terraform with Crossplane?" is: it depends on what you're managing and who's operating it. Crossplane is the better fit when:

  • Your team already runs Kubernetes and wants a single control plane for both workloads and infrastructure.
  • Continuous drift correction is more important than explicit apply/plan cycles — you want Azure to always match Git, not just after a pipeline run.
  • You're building platform abstractions for multiple application teams and want a proper API surface with schema validation.
  • Your provisioning frequency is high enough that Terraform state lock contention is a real operational problem.

Terraform remains the better fit when infrastructure is large and complex (many interdependent resources where graph planning matters), when you need plan review before changes are applied (Crossplane acts immediately on spec changes), or when the team has deep existing Terraform expertise and the operational overhead of a new control plane isn't justified.

In practice, most mature environments end up with a hybrid: Crossplane for the infrastructure closely tied to application workloads (databases, queues, storage, Key Vaults), and Terraform or Bicep for the platform layer (VNets, AKS clusters, hub-spoke networking) where changes are infrequent, carefully reviewed, and benefit from explicit plan approval workflows.

What to think about before adopting Crossplane

A few things I'd want to have thought through before going to production:

  • Provider API coverage: provider-azure-upbound has broad coverage but not every Azure resource type is fully supported. Check the provider changelog for your specific resources before committing — some newer Azure services lag by months.
  • RBAC for the provider identity: the managed identity Crossplane uses is a very powerful principal. Scope its permissions to the minimum necessary resource groups, and audit what it can do. Contributor at subscription scope is too broad for most setups.
  • Secret management: Crossplane can write connection details (connection strings, keys) into Kubernetes Secrets after provisioning a resource. Those secrets need to be handled with care — store them in Key Vault via External Secrets Operator rather than leaving them as plain Kubernetes Secrets.
  • Cluster dependency: your Azure infrastructure lifecycle is now coupled to your AKS cluster's availability. If the cluster is down, Crossplane can't reconcile. For critical infrastructure, consider whether this coupling is acceptable and what your recovery procedure is.
