Kargo for Multi-Cluster GitOps: Promoting Across Argo CD Instances with Entra ID SSO

Roman Rabodzei · Oct 2026 · ~8 min read
Kargo Argo CD GitOps AKS Entra ID Platform Engineering

We run several AKS clusters for a data platform, each hosting its own Argo CD instance. That worked fine until we needed a consistent, auditable way to promote the same set of container images — nine independently versioned batch-processing jobs — through dev, test, acceptance, and production without hand-editing Application manifests or building another bespoke pipeline stage per environment. We settled on Kargo, and getting Entra ID SSO, a remote Argo CD target, and Application Gateway ingress to all cooperate turned into one of the more genuinely enjoyable setup exercises I've had this year.

Why a management cluster, not a sidecar install

Kargo's default story assumes it sits next to the Argo CD instance it promotes into. We didn't want that: the cluster running our Argo CD was already tight on system-pool capacity, and installing Kargo's six components there meant competing with AGIC, cert-manager, and kube-system for a single small node. Instead, Kargo runs on a separate management cluster with its own user node pool, and its controller talks to the remote cluster's Argo CD entirely through controller.kubeconfigSecrets.argocd — a mounted kubeconfig built from a ServiceAccount token on the remote side, stored in Key Vault, and turned into a Kubernetes Secret at deploy time.

The remote-side RBAC is a namespaced Role, not a ClusterRole, scoped to argoproj.io/applications read access in the Argo CD namespace. That means controller.argocd.watchArgocdNamespaceOnly has to be set to match — leave it at the chart default and Kargo's controller tries to watch Applications cluster-wide, which fails with a blunt "forbidden at the cluster scope" the moment it starts. The chart's own local Argo CD RBAC (argocd.dataPlane.install and argocd.dataPlane.kargoController.install) is meaningless in this topology and should be disabled — it grants access to an Argo CD on the management cluster that doesn't exist.

Entra ID SSO: the app registration type actually matters

Kargo's OIDC config is standard — issuer URL, client ID, a CLI client ID for kargo login --sso — but two Entra-specific details aren't obvious until you hit them:

  • The UI app registration has to be a Single-Page Application, not Web. Entra requires a client secret for a Web app registration, which conflicts with Kargo's secretless PKCE authorization code flow. Register it as "Web" and the redirect silently fails to exchange the code.
  • Entra doesn't expose group membership as a requestable OAuth scope. Kargo's chart default for oidc.additionalScopes is [groups] — meant for IdPs like Okta or Auth0 that have a literal groups scope. Request it against Entra and you get a blunt AADSTS650053: application asked for scope 'groups' that doesn't exist on the resource (Microsoft Graph). Group membership comes through the ID token's groups claim instead — configured once under the app registration's Token configuration — so additionalScopes should be empty and usernameClaim set to whichever claim your tenant actually populates (we use email).

Until a dedicated security group exists for platform access, admin binding can fall back to an explicit list of email claims rather than a groups claim — just be aware that claim matching is exact-string and case-sensitive, and Entra's actual casing in the token won't necessarily match how a UPN is written anywhere else (the Portal, an onboarding doc, your own config history). The admin account with a password hash stays enabled as a break-glass fallback, injected from Key Vault at install time rather than committed anywhere.

Debugging tip: when a claim-based binding doesn't behave as expected, Kargo's API logs the actor identity on every request (e.g. an "actor": "email:..." field) — that's the fastest way to confirm the exact string and casing Entra is actually sending, rather than guessing from the token configuration pane.

TLS, SSE, and Application Gateway

Ingress is managed by AGIC (Azure Application Gateway Ingress Controller), terminating TLS at the gateway rather than in-cluster — so Kargo's API runs with api.tls.enabled: false and terminatedUpstream: true, which forces the UI's generated URLs and OIDC redirects to still resolve as https even though the pod itself only serves plain HTTP. The one setting worth calling out is connection draining: Kargo's UI uses gRPC-Web and long-lived server-sent-event streams for live promotion status, and the default AGIC timeouts cut those streams mid-flight. Bumping appgw.ingress.kubernetes.io/connection-draining and its timeout, plus the general request-timeout annotation, fixed intermittent "stuck" promotion views in the UI without touching anything upstream.

Warehouses, per-image SemVer, and a Freight pile-up

Each of the nine batch-job images is independently tagged and released from its own CI pipeline, so the Warehouse subscribes to each image repository separately with a SemVer image selection strategy and a one-hour discovery interval, rather than one subscription watching a single umbrella tag. That independence is also what caused our one real operational surprise: Kargo's garbage collector default for minFreightDeletionAge is 336 hours (two weeks) — reasonable if Freight is created in lockstep across a small number of images, but with nine images versioning independently, far more Freight was being created than was ever promoted, and it piled up unpruned in the UI well before the two-week mark. Shortening that to 168 hours (one week) matched our actual promotion cadence and kept the Freight list usable.

Project-level access — who can view, promote into, or administer a specific Kargo Project — is a separate, finer-grained mechanism from the cluster-wide admin claims above, applied per-project with kargo grant --project=<project> --role=<role> --claim=... rather than baked into the Helm values.

What I'd tell a team setting this up fresh

  1. Decide early whether Kargo lives next to an Argo CD it drives, or on its own management cluster reaching a remote one — the RBAC shape (ClusterRole vs. namespaced Role) and watchArgocdNamespaceOnly follow directly from that choice.
  2. Register the Entra app as a Single-Page Application, leave additionalScopes empty, and configure the groups claim under Token configuration rather than requesting it as a scope.
  3. If you're behind AGIC, tune connection draining before you assume the UI's live updates are broken — it's very often just the default timeout cutting the SSE stream.
  4. Size minFreightDeletionAge to how many independently-versioned image subscriptions your Warehouse actually has, not the chart default.
