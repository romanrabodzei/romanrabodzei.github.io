Microsoft Copilot Harness in Foundry Agent Service: One Runtime Across the Stack

Roman Rabodzei · Nov 2026 · ~5 min read
Microsoft Foundry GitHub Copilot AI Agents Agent Service Microsoft 365

Microsoft shipped the Copilot harness inside Foundry Agent Service in late October, and the framing in the announcement is worth paying attention to: "one uniform Copilot across the stack." That's a statement about architecture, not marketing — it means Microsoft 365 Copilot, GitHub Copilot, and custom agents built on Foundry are converging onto a shared runtime rather than being separately engineered products that happen to share a brand name.

What a "harness" actually is

In agent terminology, a harness is the runtime layer that wraps a model: it manages tool calling, conversation and task state, memory, and the loop that decides when the agent is done versus when it needs another turn. Two products both called "Copilot" can behave very differently if they're running on different harnesses — different tool-calling conventions, different memory models, different failure modes. Unifying the harness means those behaviors converge: the same underlying contract for how an agent calls tools, remembers context, and decides when to stop applies whether you're inside Microsoft 365, a GitHub PR, or a custom Foundry agent.

Why this matters more than another feature announcement

  • Consistency of behavior. Teams building custom agents on Foundry get the same underlying execution model Microsoft's own first-party Copilot surfaces run on, rather than a lighter-weight or differently-behaved variant.
  • Shared improvements propagate. A harness-level fix or capability — better tool-call reliability, improved long-context handling — benefits every surface built on it at once, instead of needing separate fixes per product.
  • Lower cost of building a serious custom agent. If the harness underneath your custom Foundry agent is the same one powering GitHub Copilot's coding agent, you inherit a runtime that's already been hardened under production load, rather than bootstrapping agent plumbing from scratch.

Practical implication: if you're currently building a custom agent on Foundry and hand-rolling your own tool-calling and state-management loop, it's worth checking whether adopting the shared Copilot harness removes that layer of custom plumbing entirely — that's exactly the kind of undifferentiated work a unified harness is meant to absorb.

The trade-off worth watching

Convergence onto a shared harness also means less room to diverge for workloads with genuinely different requirements — a latency-sensitive inline coding suggestion and a long-running autonomous research agent have different ideal runtime characteristics, and a single harness has to serve both reasonably well rather than being perfectly tuned for either. Microsoft's bet is that the behavioral consistency and shared improvement velocity outweigh that loss of specialization, at least for the majority of use cases that aren't at the extreme ends of the latency/autonomy spectrum.
