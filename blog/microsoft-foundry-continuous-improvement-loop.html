The Continuous Improvement Loop in Microsoft Foundry: Establish, Identify, Optimize, Validate

Roman Rabodzei · Nov 2026 · ~6 min read
Microsoft Foundry AI Agents MLOps Observability Azure AI

Microsoft used Ignite 2026 to bring a continuous-improvement loop to Microsoft Foundry: agents don't just get built and shipped, they get watched, measured against candidate fixes, and re-shipped once a change clears a statistical bar — without a human writing the retraining pipeline by hand. The idea itself isn't new to MLOps, but packaging it as a first-class Foundry workflow, with a named four-step cycle, is worth a closer look at what's actually automated versus what still needs a human to decide.

The four-step cycle

Foundry frames the loop as Establish → Identify → Optimize → Validate, repeating. Each pass is supposed to build on the evidence the previous one produced, rather than starting over.

  • Establish — define "good." Rubric evaluators score responses against written criteria (now covering safety as well as quality), built from annotated real traces rather than hypothetical test cases. A locked-in "golden dataset" becomes the benchmark every new version has to beat before it ships.
  • Identify — find problems from real usage. Insights groups recurring failures from production traces, attaches supporting evidence, and suggests a likely cause — so triage starts from "this failure pattern affects 8% of runs" rather than a pile of unsorted logs. This also covers agents built outside Foundry entirely, on LangGraph, LangChain, or CrewAI.
  • Optimize — generate and test candidate fixes. An agent optimizer adjusts instructions, skills, or model choice, and evaluates each candidate against the rubrics from Establish before anything reaches production. Skill updates are versioned, so a team can roll one back or reuse a proven one across agents rather than re-discovering it.
  • Validate — prove the change is real, then repeat. A statistical test checks whether a new version is actually better or just noisy variance, with the same checks runnable inside GitHub Actions or Azure DevOps as a CI/CD gate. Whatever ships becomes the new baseline, and any regression it introduces becomes next round's Identify input.

What the agent optimizer doesn't do

The part worth being precise about: the optimizer proposes and ranks candidate changes, it doesn't auto-deploy them. Microsoft's own framing is that "nothing changes in production until you apply it" — the loop automates the expensive parts (generating candidates, running them against the evaluation rubric, surfacing the strongest option) and leaves the ship decision to a person. That's a meaningfully different claim than "agents that retrain themselves," and it's the right design for anyone who's been burned by an automated pipeline that shipped a regression nobody reviewed.

Where this plugs into existing practice: if you already run evaluation suites and rubric-based scoring for agents outside Foundry, Insights and the agent optimizer are mainly replacing the manual triage step between "something regressed" and "here's a tested candidate fix" — not replacing your evaluation strategy itself.

The numbers, with the obvious caveat

Microsoft's post leans on customer examples to make the loop concrete. Alaska Airlines tuned MAI-Code-2-Flash to classify aircraft maintenance reports by ATA code, going from 81.2% accuracy out of the box to 91.1% after tuning — with qualified staff still making the final call. Heidi, a clinical AI assistant, used Programmed Training to post-train an open-weight model that reportedly matches a frontier model on clinical note quality at an estimated 87% lower cost per note. Docusign and NTT DATA are cited applying the same loop at larger scale. All of these are vendor- or customer-reported, with no independent benchmark or methodology published alongside them — useful as directional evidence that the loop works in production, not as a number to cite without the source attached.

GA versus preview — what you can actually use today

  • Generally available now: Insights, observability for LangGraph/LangChain/CrewAI agents, hosted agent concurrency, voice agents, prompt optimization, the model router, and continuous evaluation of live traffic.
  • Still in preview: safety rubric evaluators, trace annotations, evaluation and golden datasets, sending Insights straight into the agent optimizer, skill and cost optimization, Programmed Training, and — notably — hosted agents on AKS, which Microsoft lists as "coming soon" rather than shipped.

That last item is worth flagging for anyone running Foundry workloads alongside an existing AKS footprint: the loop described here is Foundry-native today, and the bridge to running hosted agents directly on your own Kubernetes clusters is explicitly not there yet. Worth checking back on before planning an architecture around it.
