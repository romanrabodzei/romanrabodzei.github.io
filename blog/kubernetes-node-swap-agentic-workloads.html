Scaling Kubernetes Workloads with Node Swap: Memory Headroom for Agentic AI

Roman Rabodzei · Nov 2026 · ~6 min read
Kubernetes AKS Memory Management AI Workloads Node Swap

Kubernetes' node swap support — stable since v1.33 — is getting fresh attention for a reason that has nothing to do with its original use case. It was designed for general memory-pressure relief on constrained nodes. What's making it relevant now is agentic AI workloads: they frequently demand a large memory footprint just to start up and load context, well before steady-state usage settles down, and that startup spike is exactly the kind of transient pressure swap is good at absorbing.

Why memory, not CPU, is the first hard limit

A cluster typically runs out of RAM long before it runs out of CPU. CPU is throttleable and shareable in ways memory simply isn't — once a container's resident set exceeds what's available, the only options are evict, OOM-kill, or page to disk. Agentic workloads make this worse specifically at startup: loading a large model context, initializing an inference runtime, or warming an in-memory cache can spike memory usage well above steady-state, and if the node has no headroom for that spike, the pod gets killed before it ever reaches steady state.

What node swap actually changes

Swap support lets the kubelet allow specific workloads to page memory to disk instead of being killed outright when they exceed their memory request during a transient spike. It's configured per node and respects pod QoS class — Burstable pods can be configured to use swap, while Guaranteed-class pods are excluded by default, since their whole contract is predictable, non-degraded performance. The practical effect for an agentic workload: a startup memory spike that would previously trigger an OOM kill now has somewhere to spill to, buying enough time to get past initialization and settle into its real working set.

What it doesn't fix

  • It's not a substitute for correct resource requests. Swap absorbs a transient spike; it does not make a persistently undersized memory request workable. Sustained reliance on swap means degraded performance from disk I/O, not a free capacity increase.
  • It doesn't apply to Guaranteed QoS pods by default — which is the right call, but means teams running latency-sensitive inference at Guaranteed QoS won't get this safety net without deliberately reconsidering that QoS class for the workload.
  • Disk-backed swap is slow relative to RAM. This is a startup-spike mitigation, not a design pattern for workloads that are routinely memory-constrained in steady state.

Where to actually use this: Burstable-QoS batch and inference workloads with a known, bounded startup memory spike — not as a blanket policy across a node pool, and not as a way to avoid right-sizing memory requests for workloads that are chronically tight on RAM.

Enabling it on AKS

Swap requires kubelet configuration at the node pool level (swap behavior and size), and on managed Kubernetes like AKS this typically means a dedicated node pool for workloads that need it, rather than a cluster-wide default. Pair it with monitoring on swap utilization specifically — sustained swap usage on a node is a signal that the underlying memory requests need to go up, not that swap is doing its job well.
