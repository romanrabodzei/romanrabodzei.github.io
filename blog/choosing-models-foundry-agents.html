Choosing Models for Production Agents: GPT-6, Claude Opus 5.5 and Beyond

Roman Rabodzei · Oct 2026 · ~8 min read
Microsoft Foundry AI Agents Model Selection FinOps GPT-6

September 2026 brought a wave of new model availability into Microsoft Foundry and GitHub Copilot at once: GPT-6 Astra, GPT-6 Sol, and GPT-6 Luna for production agents, Claude Opus 5.5 for long-running coding and knowledge work, plus Grok 4.7 and Gemini 3.8 Flash showing up in Copilot's model picker. Azure's own messaging has been explicit about this: "the best model for your business will keep changing." That's true, and it means model selection needs to be a repeatable process, not a one-time decision baked into your agent's code.

Stop thinking in terms of "the model" for an agent

The single biggest mistake I still see is treating model choice as one decision for the whole agent. A well-designed agent has subtasks with very different requirements: classification, extraction, summarisation, multi-step reasoning, and code generation don't need the same model, and routing all of them through the most capable (and most expensive) option available is the most common source of avoidable cost I've seen in agent deployments this year.

What the September lineup is actually good at

// GPT-6 Astra

Positioned as the frontier option — reserve it for the reasoning-heavy steps in an agent's workflow where quality genuinely depends on the strongest available model: complex multi-step planning, ambiguous instruction interpretation, and tasks where a wrong answer is expensive. It's the most costly option in the lineup, so use it deliberately rather than as the default.

// Claude Opus 5.5

Explicitly positioned for long-running coding and knowledge work — a good fit for agents that need to maintain context across an extended task (a multi-file refactor, an extended research synthesis) rather than a single quick response. If your agent's workload looks like "sustained work over many steps," this is worth benchmarking against Astra for your specific task before defaulting to the frontier model.

// GPT-6 Sol and GPT-6 Luna

Framed around scalable, high-volume tasks — the models to route simple, repeated subtasks to: structured extraction, classification, straightforward transformations. These are the models that should be handling the bulk of an agent's individual tool calls, with the expensive frontier model reserved for the steps that actually need it.

Practical exercise worth doing this month: take your highest-traffic agent, log which model handles each subtask type today, and calculate what percentage of your monthly token spend goes to subtasks that don't actually need frontier-model quality. In every agent I've audited this way, it's been higher than the team expected.

A repeatable model selection process

  1. Baseline on the best model during development to establish the quality ceiling for each subtask type.
  2. Systematically test cheaper models against that baseline, subtask by subtask, using real production examples rather than synthetic test cases.
  3. Set a quality threshold, not a model preference — route to the cheapest model that clears the threshold for each subtask, and re-evaluate that routing whenever a new model becomes available.
  4. Re-run the evaluation on a schedule, not just when a new model launches — model provider pricing and capability both shift, and yesterday's optimal routing decision doesn't stay optimal indefinitely.

Why this needs to be infrastructure, not a one-off decision

The model catalogue in Microsoft Foundry, combined with token rate-limiting and semantic caching (both covered in Azure's Economics of Agent Optimization series this year), makes model routing a first-class platform capability rather than something each agent team reinvents. If you're running more than a couple of agents in production, building a shared evaluation harness and routing configuration once — rather than letting every team hardcode a model choice — pays for itself quickly as new models continue to arrive at this pace.
