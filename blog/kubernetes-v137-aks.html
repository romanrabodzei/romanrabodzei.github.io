Kubernetes v1.37 on AKS: Pod Certificates, Cluster Trust Bundles, and Metrics API v1

Roman Rabodzei · Sep 2026 · ~9 min read
AKS Kubernetes v1.37 Pod Certificates Cluster Trust Bundles Metrics API AKS

Kubernetes v1.37, released in late August 2026, is a security and operations release with three changes worth watching: Pod Certificates, Cluster Trust Bundles, and the Metrics API graduating to v1. The important qualification for AKS teams is that upstream availability and managed-service availability are different things. A feature can be stable in Kubernetes and still wait for an AKS version, preview, or add-on to expose it. Treat this as an operator's guide to what v1.37 changes and what to verify before upgrading.

What actually changed in v1.37

Kubernetes follows a staged feature model. A feature can be alpha, beta, or stable, and a stable API is not the same as a vendor-managed feature being immediately available in every distribution. In v1.37, the headline changes are:

  • Pod Certificates: workloads can request short-lived X.509 certificates through a Kubernetes-native API, reducing the need for custom certificate bootstrapping.
  • Cluster Trust Bundles: cluster operators can publish trusted CA bundles for workloads to consume, making trust distribution more consistent than copying CA files into individual images.
  • Metrics API v1: the resource metrics API behind kubectl top and resource-based autoscaling becomes stable, strengthening the contract for operators and autoscaling integrations.

The release is less about a flashy new controller and more about making identity, trust, and resource measurement first-class platform primitives. That is exactly the sort of change that tends to matter six months later, when a platform team is operating hundreds of workloads and needs consistent defaults rather than another one-off sidecar.

Pod Certificates: workload identity without another sidecar

Pod Certificates provide a Kubernetes API for requesting and rotating short-lived certificates for workloads. The kubelet can obtain certificates on behalf of a pod, while the workload reads the resulting material from a projected volume. The exact issuer and signer configuration still belong to the cluster operator, but the application no longer needs to own a long-lived private key or implement its own renewal loop.

For AKS, this is potentially useful for internal mTLS, workload-to-workload authentication, and systems that already understand SPIFFE-like short-lived identities. It is not a replacement for every certificate service. Before adopting it, verify that the AKS version exposes the API, that your chosen issuer is supported, and that the workload identity and rotation behaviour are documented for your cluster configuration.

Do not confuse upstream stability with AKS support: check the current AKS release notes and feature documentation before enabling Pod Certificates or Cluster Trust Bundles. A stable Kubernetes API still depends on the managed control plane, node image, admission configuration, and supporting add-ons being available in your target AKS version.

Cluster Trust Bundles: making CA distribution explicit

Trust distribution is easy to get wrong. A team adds a CA certificate to an image, another mounts it from a Secret, and a third downloads it during startup. Cluster Trust Bundles give operators a standard object for publishing trusted roots and give workloads a consistent way to consume them. The trust material can then be updated independently from application images.

This matters in environments with private endpoints, internal PKI, service meshes, or multiple certificate authorities. It also gives security teams a cleaner ownership boundary: platform operators publish approved roots, while application teams consume them without distributing copies through every repository. 

apiVersion: certificates.k8s.io/v1alpha1
kind: ClusterTrustBundle
metadata:
  name: platform-root-ca
spec:
  trustBundle: |
    -----BEGIN CERTIFICATE-----
    ...approved root certificate...
    -----END CERTIFICATE-----

The example shows the shape, not a complete production manifest. Trust bundle APIs and feature gates should be validated against the exact v1.37 documentation and the AKS version you run. Keep the source of truth in Git, review changes like code, and alert when a bundle is approaching expiry or changes unexpectedly.

Metrics API v1: a stronger contract for autoscaling

The Metrics API provides CPU and memory usage for nodes and pods. It is the API behind kubectl top and resource metrics used by horizontal and vertical autoscaling. Moving to a stable v1 contract reduces the uncertainty for platform tooling that depends on resource measurements, but it does not remove the need to operate the Metrics Server and verify that metrics are fresh.

  • Check kubectl top nodes and kubectl top pods -A after the upgrade.
  • Confirm the Metrics API reports Available and that timestamps are recent.
  • Test an HPA in a non-production namespace before relying on the new API during a workload event.
  • Keep Prometheus or Azure Monitor for long-term history; the Metrics API is for current resource usage, not durable observability.

What this means for an AKS upgrade

  • Check the AKS support matrix: confirm the target Kubernetes version is offered in your region and that the v1.37 features you need are enabled in that AKS release.
  • Review feature gates: Pod Certificates and trust bundle behaviour may depend on feature gates, issuers, or add-ons. Do not copy an upstream manifest directly into a managed cluster.
  • Validate add-ons: test Metrics Server, Azure Monitor, policy integrations, admission controllers, and workload identity after the control-plane and node-pool upgrade.
  • Test certificate rotation: deploy a disposable workload, inspect the projected certificate, wait through a rotation cycle, and confirm the application reloads it correctly.
  • Keep rollback realistic: Kubernetes upgrades are forward operations. Back up critical manifests and define how you will restore workloads if an add-on or admission policy behaves differently.

What I'd recommend for AKS teams

Do not upgrade a production AKS cluster solely because an upstream release has an attractive feature. First confirm AKS support, then test the feature in a disposable cluster with the same policies, add-ons, and workload identity configuration as production.

The most immediately useful v1.37 change is probably Metrics API v1 because it strengthens a common operational dependency. Pod Certificates and Cluster Trust Bundles are more strategic: they can simplify workload mTLS and trust distribution, but only after the issuer, RBAC, and rotation story is fully understood.
