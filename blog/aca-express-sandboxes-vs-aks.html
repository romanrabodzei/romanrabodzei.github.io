Azure Container Apps Express & Sandboxes: Is AKS Still Necessary?

Roman Rabodzei · Oct 2026 · ~8 min read
Azure Container Apps AKS Architecture Platform Engineering AI Agents

In September 2026, two Azure Container Apps features that had been in preview since earlier this year — Container Apps Express and Container Apps Sandboxes — reached general availability. Neither is a small addition. Express collapses the path from code to a running, scaled container down to something close to a single command, and Sandboxes give you isolated, short-lived execution environments designed specifically for running untrusted or AI agent-generated code safely. Taken together, they close a meaningful part of the gap that used to push teams toward AKS by default.

I run both platforms in production, and the question I keep getting asked internally is some version of "do we still need a cluster for this?" The honest answer is: for a growing share of workloads, no — but not for all of them. Here's how I've been drawing that line.

What actually shipped

Container Apps Express is aimed squarely at reducing the operational surface area between a developer and a running service. It streamlines build, revision management, and scaling defaults so that shipping a container doesn't require someone to first design ingress rules, scaling rules, and Dapr sidecars by hand. It's the same underlying platform — Container Apps was always built on a managed Kubernetes and KEDA foundation — just with far fewer decisions exposed to the person deploying.

Container Apps Sandboxes solves a different, newer problem: how do you safely execute code you didn't write and don't fully trust? That's increasingly the shape of workloads coming out of agentic AI systems — a Foundry agent that generates a Python snippet to transform data, or a Copilot workflow that needs to run arbitrary user-submitted code. Sandboxes give you fast-starting, strongly isolated execution contexts with tight resource and network boundaries, without having to hand-roll gVisor or Kata configuration on self-managed nodes.

Why this matters right now: a lot of the AI agent architectures I'm seeing this year need exactly this pattern — an orchestrator that occasionally needs to execute code it did not author, in a boundary strict enough to trust with production data. Before Sandboxes, building that boundary yourself on AKS was real engineering work.

Where Container Apps already covered the ground

Even before this GA, Container Apps was the right choice for a large share of what teams reach for AKS to do: stateless HTTP APIs and background workers, event-driven scaling with KEDA, blue-green revisions, and Dapr-based service-to-service communication. None of that required cluster-level thinking — no node pool sizing, no CNI choice, no cluster upgrade cadence to plan around. Express just makes that path faster to reach, and Sandboxes extend it into a category — untrusted code execution — that previously had no first-class managed answer on Azure at all.

Where AKS still earns its complexity

I don't think this GA changes the calculus for workloads that actually need Kubernetes primitives rather than just "a place to run a container." The list I keep coming back to:

  • Custom networking requirements — Azure CNI Overlay tuning, network policies, service mesh (Istio/Cilium), or hybrid connectivity patterns that need node-level control.
  • GPU and specialised node pools — training or high-throughput inference workloads that need specific VM SKUs, taints/tolerations, and scheduler-level placement control.
  • Multi-tenant platform engineering — when you're building an internal platform on top of Kubernetes primitives (namespaces, admission controllers, custom operators) for other teams to consume.
  • Existing operational investment — GitOps pipelines, custom operators (Crossplane, cert-manager, external-secrets), and observability stacks already built around the Kubernetes API are expensive to walk away from without a compelling reason.
  • Fine-grained scheduling control — workload-aware scheduling, pod-level resource management, and the kind of scheduler behaviour Kubernetes v1.37 keeps extending (more on that in the next post).

A decision framework I actually use

When a new service is proposed, I ask three questions before defaulting to AKS:

  1. Does this workload need anything below the container boundary — specific nodes, custom CNI, GPU scheduling? If no, that's a point against AKS.
  2. Is this "run my code" or "run untrusted code"? Sandboxes now answer the second case directly, which used to be a strong AKS argument on its own.
  3. Is there already a platform team maintaining shared Kubernetes infrastructure that this workload can ride on for free? If yes, the marginal cost of adding one more workload to an existing cluster is usually lower than standing up a new Container Apps environment.

That third question matters in practice more than the first two combined. Green-field decisions and decisions inside an organisation with a mature AKS platform team look completely different — and that's the right outcome. The tools should follow the workload and the team, not the other way around.

My take

Container Apps Express and Sandboxes don't make AKS unnecessary — they make it optional for a wider range of workloads than before, which is exactly what a managed compute layer is supposed to do. The interesting shift is for AI agent architectures specifically: Sandboxes remove one of the more painful pieces of infrastructure you'd otherwise have had to build yourself, and I'd expect it to become the default answer for "where does the agent's generated code actually run" going forward.
