Kubernetes v1.37 Storage Hardening: EmptyDir Permissions & Bind Mounts

Roman Rabodzei · Oct 2026 · ~7 min read
Kubernetes v1.37 AKS Storage Pod Security CSI

Alongside the scheduling changes in Kubernetes v1.37, there's a quieter but genuinely useful pair of storage security features: emptyDir permission modes and bind mount options for CSI volumes. Neither requires a new controller or CRD — they're small, additive API fields — but they close gaps that security-conscious platform teams have been working around with admission policies and init containers for years.

EmptyDir permission modes

emptyDir volumes have always been created with permissive default permissions, relying on the container's own process umask or an init container to lock things down before the main workload starts. v1.37 lets you set an explicit permission mode directly on the volume spec, so the directory is created with the restrictive permissions you want from the first write — no init container, no race condition where a briefly-permissive directory exists before your hardening step runs.

This matters more than it looks on the surface. A shared emptyDir between a main container and a sidecar is a common attack surface if either process runs with broader write access than it needs — a compromised sidecar with write access to a directory the main process trusts is a real privilege escalation path. Setting an explicit, restrictive mode at volume creation removes that window entirely.

Bind mount options for CSI volumes

The second change gives you finer control over how CSI-provisioned volumes are bind-mounted into containers — specifically, options like recursive read-only mounts and mount propagation control. Before this, achieving a genuinely read-only, non-propagating mount for a CSI volume required either driver-specific workarounds or accepting weaker guarantees than a hostPath-style mount would give you.

For platform teams enforcing "workloads should never be able to modify data they only need to read" — think shared configuration volumes, model artifacts mounted into inference pods, or read-only secrets projections — this gives you a standard, CSI-driver-agnostic way to enforce it at the API level rather than trusting individual driver implementations to get it right.

Where this pays off immediately on AKS: AI inference pods that mount a shared model volume read-only across many replicas. Recursive read-only bind mounts mean a compromised or misbehaving inference container genuinely cannot corrupt the shared model artifact, closing a class of incident that previously depended entirely on application-level discipline.

Turning this into a concrete AKS policy

  • Set explicit emptyDir permission modes in your Pod Security Standards baseline manifests — don't rely on init containers for this once the field is available and stable in your target Kubernetes version.
  • Default to read-only CSI mounts for any volume the workload doesn't need to write to — model artifacts, shared configuration, and reference data are the obvious first candidates.
  • Audit existing init-container-based permission hardening — once emptyDir modes are available, those init containers become redundant overhead and can be removed, shaving pod startup time.
  • Validate with your CSI driver vendor — Azure Disk CSI and Azure Files CSI support timelines for these new mount options may lag the Kubernetes API version; confirm before assuming the guarantee is enforced end-to-end.

My take

These are exactly the kind of unglamorous, additive security features that quietly remove whole classes of workaround from a platform team's manifests. Neither needs a new operator or policy engine — they just make the Kubernetes API itself capable of expressing intent that used to require external tooling. I'll be rolling explicit emptyDir modes into our Pod Security Standards baseline as soon as the AKS-supported Kubernetes version catches up to v1.37.
