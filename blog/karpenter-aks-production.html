Karpenter on AKS in Production

Roman Rabodzei · Aug 2026 · ~11 min read
AKS Kubernetes Karpenter Node Provisioning Cost Optimization GitOps

Node Auto Provisioning (NAP) — Microsoft's managed Karpenter offering on AKS — has been generally available since mid-2024, and it's been quietly replacing cluster-autoscaler as the recommended approach for clusters that need responsive, cost-efficient scaling. Having deployed and operated it on a production data workload, I want to write down what actually matters in practice: not the documentation overview, but the decisions that affect your bill and your on-call experience.

How Karpenter differs from cluster-autoscaler

Cluster-autoscaler works at the node pool level. You pre-define pools with specific VM SKUs, and the autoscaler scales them up when pods are pending and down when utilisation drops. It's conservative by design: it waits for evidence before removing a node, and it can only pick from SKUs you already have pools for. The operational shape is: you pre-plan your pools, the autoscaler manages counts within them.

Karpenter works differently. Rather than scaling a pre-existing pool, it reads pending pod requirements directly — resource requests, node selectors, taints, topology spread constraints — and provisions exactly the right node just-in-time. It can pick from any SKU that satisfies the declared constraints, making cost-optimal provisioning decisions without being locked into upfront pool definitions. Consolidation is active and continuous: it watches for underutilised nodes and reorganises them, bin-packing pods to free up nodes for deprovisioning. You define the rules; Karpenter makes the decisions.

The practical difference becomes obvious for batch or bursty workloads. With cluster-autoscaler, you'd size your pools for peak and accept idle capacity at off-peak. With Karpenter and WhenEmptyOrUnderutilized consolidation, the cluster can truly scale to zero compute when no workloads are running — paying only for the system node pool between job runs.

AKSNodeClass: image family and OS disk placement

AKSNodeClass is the Azure-specific CRD that tells Karpenter what kind of node image and OS disk to use. For most workloads today, imageFamily: AzureLinux is the right choice — it's the Microsoft-maintained image with first-class NAP support and the most timely security patching cadence.

The more interesting decision is osDiskSizeGB. This setting matters more than it initially appears: if the value you configure is small enough to fit on the SKU's local NVMe resource disk, Karpenter will provision the OS disk as ephemeral — placed on local NVMe — rather than creating a network-attached managed disk. For I/O-intensive workloads that spill to disk or use emptyDir volumes for temporary data, this is a meaningful difference in both performance and cost. No per-disk billing for the OS, and lower latency on any workload that touches /var/lib/kubelet. 

apiVersion: karpenter.azure.com/v1beta1
kind: AKSNodeClass
metadata:
  name: driverpool
spec:
  imageFamily: AzureLinux
  osDiskSizeGB: 128  # fits D8ads_v5 local NVMe → ephemeral OS, not managed disk

Verify this assumption once per image update: SSH to a freshly provisioned node and run df -h /var/lib/kubelet. If the OS landed on the local NVMe you'll see the resource disk; if it's a managed disk you'll see something like /dev/sda. The distinction matters for workloads where kubelet root is on a hot path.

NodePool: requirements, taints, and limits

The NodePool is where the provisioning logic lives. Three decisions in the requirements block matter most.

// instance-type: list, don't pin

Rather than pinning to a single SKU, list two or three closely related options. This gives Karpenter flexibility to provision whichever has capacity available in the target zone. For spot, this is essential: Azure spot capacity is regional and volatile, and a pool constrained to one SKU will fail to provision when that SKU is exhausted.

// capacity-type: spot with on-demand fallback

["spot", "on-demand"] is the practical choice for batch workloads — spot pricing when capacity is available, automatic fallback to on-demand otherwise. Karpenter handles the preference ordering. For coordinator or driver-tier nodes where mid-job eviction would be costly, ["on-demand"] is the right call even if it costs more.

// taints: hard workload isolation

Taints enforce isolation without the pods needing to do anything beyond declaring a toleration. A NoSchedule taint on a pool means only tolerating pods land there — no accidental co-scheduling of platform pods onto expensive executor nodes. This also enables clean per-pool cost attribution in Azure Cost Management. 

apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: spotexecpool
spec:
  template:
    spec:
      nodeClassRef:
        group: karpenter.azure.com
        kind: AKSNodeClass
        name: spotexecpool
      requirements:
        - key: node.kubernetes.io/instance-type
          operator: In
          values:
            - Standard_E16ads_v5
            - Standard_E16ads_v7
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]   # spot preferred, on-demand fallback
        - key: topology.kubernetes.io/zone
          operator: In
          values: ["eastus2-1", "eastus2-2", "eastus2-3"]
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64"]
      taints:
        - key: workload
          value: spark-executor
          effect: NoSchedule
  limits:
    cpu: "512"       # bounds blast radius: max ~32 E16 executor nodes
    memory: "4Ti"
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m

Scale-to-zero and disruption tuning

WhenEmptyOrUnderutilized is the most aggressive consolidation policy. For batch workloads with clear job boundaries — where the cluster should be quiet between runs — it's the right choice. Karpenter will deprovision nodes as soon as they're empty or can be consolidated elsewhere. The consolidateAfter window is how long it waits after a node becomes underutilised before acting.

The window matters. For transient job pods that complete in minutes, a 1–2 minute consolidation window means the cluster returns to near-zero compute cost shortly after each run completes. For coordinator nodes handling longer-lived driver processes, a slightly longer window (2m) reduces unnecessary churn. For truly stateful or sensitive workloads, WhenEmpty is the safer policy: it only deprovisions nodes that have nothing running, never attempting to move live pods.

The cost implication of scale-to-zero: a cluster running nightly batch jobs with Karpenter and WhenEmptyOrUnderutilized pays for executor compute only during the job windows — not for idle capacity at 2pm. Combined with spot pricing on executor nodes, this is often the single biggest lever on a data platform's AKS bill.

Resource limits: bounding the blast radius

NodePool limits cap the total CPU and memory Karpenter will provision for that pool. This is your circuit breaker. A misconfigured job that spawns thousands of executor pods won't run up an unbounded bill — Karpenter simply won't provision nodes beyond the declared ceiling, and the excess pods stay pending until capacity is freed.

Size limits based on your maximum intended concurrency, with headroom. If your largest job needs at most 32 executor nodes at 16 vCPUs each, a CPU limit of 512 is a comfortable ceiling. Set it too tight and you'll throttle legitimate peak workloads; set it too loose and you've defeated the purpose. Review actual peak usage from Azure Monitor after a few weeks of production traffic and adjust.

Multi-zone requirements

Explicitly listing the zones your workload can run in matters for two reasons: availability (Karpenter won't attempt a zone where your SKU is unavailable) and spot quota (Azure spot quotas are sometimes zone-specific). If you omit zone requirements and Karpenter tries to provision in a zone with limited spot capacity for your target SKU, you'll see slow or failed provisioning without an obvious error.

For workloads that use distributed storage or zone-affinity networking, you may also want to constrain your NodePools to match the zones where that storage lives, to avoid cross-zone traffic costs for high-throughput I/O paths.

Deploying NodePools via GitOps

If you're running ArgoCD for workload delivery, NAP configuration should be its own ArgoCD Application with sync-wave: "-1". This ensures NodePool and AKSNodeClass resources are reconciled before any workload Application attempts to schedule pods that depend on them. Without this, you risk a race where pods land on the wrong pool or stay pending until the next sync cycle. 

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nap-config
  namespace: argocd
  annotations:
    argocd.argoproj.io/sync-wave: "-1"  # provision before workload apps
spec:
  source:
    repoURL: git@ssh.dev.azure.com:v3/your-org/your-repo/your-repo
    targetRevision: main
    path: k8s/nap
  destination:
    server: https://kubernetes.default.svc
    namespace: default
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - ServerSideApply=true  # required: Karpenter owns status fields ArgoCD would otherwise conflict on

ServerSideApply: true is required. Karpenter manages certain fields on NodePool objects (status, some annotations) that ArgoCD would overwrite or conflict with under a client-side apply model. Without it, you'll see reconciliation errors that are non-obvious to diagnose.

What to watch out for in production

  • Azure Spot quota: spot quota is separate from regular compute quota and isn't always pre-provisioned. Verify your quota for the target SKU family in the target region before go-live. A provisioning failure at 2am on a critical batch job run is not the time to discover a quota gap.
  • ARM API throttling: at high provisioning frequency — rapid successive job submissions — Karpenter can hit Azure Resource Manager rate limits. Monitor the karpenter namespace logs for provisioning delays, and if you see throttling, stagger job submissions or request a quota increase on ARM API calls.
  • PodDisruptionBudgets and consolidation: Karpenter respects PDBs during consolidation. For long-running processes (driver pods mid-job, for example), set appropriate PDBs to prevent Karpenter from evicting them during an aggressive consolidation cycle.
  • SKU availability at provisioning time: even with a well-designed NodePool requirements list, spot SKU availability can be zero during regional capacity crunches. Test your fallback behaviour before production, and consider whether a cold-start timeout SLA is acceptable for your workload.
  • Node image updates: NAP updates node images periodically. This can trigger node replacement during a consolidation cycle. If your workloads are sensitive to node churn, set maintenance windows or use disruption budgets to control when replacements happen.

What I'd do differently starting a new project today

If I was setting up Karpenter on AKS from scratch right now:

  1. Enable NAP at cluster creation time — retrofitting it onto an existing cluster that already has autoscaler-managed node pools requires careful migration sequencing.
  2. Start with WhenEmpty consolidation and switch to WhenEmptyOrUnderutilized only after validating that workload disruption tolerance is in place (PDBs, toleration on retry logic).
  3. Define pool limits conservatively on day one; loosen them based on actual observed peak rather than estimates.
  4. Put NAP configuration in a dedicated ArgoCD Application with sync-wave -1 on day one — don't mix it with workload manifests and think you'll separate it later.
  5. Verify ephemeral OS disk placement on every SKU in your NodePool list. Not all SKUs support it, and the behaviour difference between a local NVMe OS disk and a network-attached managed disk is significant for I/O-heavy workloads.

The recurring theme is that NAP's value — scale-to-zero, spot fallback, just-in-time provisioning — only delivers fully when the NodePool design is deliberate. It's not a drop-in replacement for cluster-autoscaler that you configure once and forget. The abstractions are richer, the knobs matter more, and the cost implications of getting them right are real.
