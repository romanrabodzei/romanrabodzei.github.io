Modern Supply-Chain Security: Stage-Only Tokens, Trusted Publishing, and Secret-Blocking on GitHub

Roman Rabodzei · Oct 2026 · ~8 min read
Supply Chain Security GitHub Actions npm CodeQL Application Security

September 2026 was a dense month for supply-chain security features across GitHub and npm — multiple trusted publishing configurations, stage-only tokens, automatic Dependabot registry access, secret-exposed PR blocking, and CodeQL improvements all shipped within a few weeks of each other. Individually each is a small change. Put together, they represent a genuine shift in how much of the software supply chain can now run without a long-lived credential sitting in a secrets store waiting to be exfiltrated.

Stage-only npm tokens

Stage-only npm tokens let you scope a publish token to only work from a specific, pre-declared CI stage or environment — meaning even if a token is somehow leaked, it's useless outside the exact automation context it was issued for. This is a meaningful improvement over granular-but-still-portable tokens: the token itself becomes non-transferable rather than just narrowly scoped by permission.

Multiple trusted publishing configurations for npm

Trusted publishing (OIDC-based, tokenless publishing from CI to a package registry) already existed for npm, but was limited to a single publishing configuration per package. The September update allows multiple trusted publishing configurations per package — supporting the very common real-world case of publishing the same package from more than one workflow, repository, or environment (a release workflow and a manual hotfix workflow, for example) without falling back to a shared long-lived token as the lowest common denominator.

If your team still publishes npm packages using a classic automation token stored as a repository secret, this removes the last common excuse for not migrating to trusted publishing — multi-workflow publishing was the main scenario trusted publishing didn't cleanly support until now.

Blocking pull requests with exposed secrets from merging

Secret scanning has existed for a while, but blocking the merge itself — rather than just alerting after the fact — closes the window between "a secret was committed" and "a secret is now in the default branch, in the git history, potentially already scraped by an automated credential harvester." Merge blocking on detected secrets is one of those controls that should have been the default years ago; worth enabling as a required check across every repository that has secret scanning available.

Automatic Dependabot access to GitHub-hosted registries

A smaller but practically useful change: Dependabot now gets automatic access to GitHub-hosted package registries without additional configuration, removing a class of "Dependabot silently failed to open a PR because it couldn't reach an internal registry" issues that used to require manual credential setup.

CodeQL: broader language coverage, agentic autofix

CodeQL 2.26 and 2.27 added Linux ARM64 support, improved GitHub Actions-specific security detections, and extended C/C++ and Kotlin query coverage. Combined with the newer "remediate Code Quality findings with agentic autofix" capability, code scanning is moving from "flag the problem" toward "propose the fix as a reviewable pull request" — worth piloting on a lower-risk repository first to calibrate how much you trust the generated fixes before turning it on broadly.

Practical priority order if you're catching up on all of this at once: merge-blocking on exposed secrets first (highest risk reduction, lowest effort to enable), trusted publishing migration second (removes standing credentials), then CodeQL coverage expansion and agentic autofix piloting as ongoing work rather than a one-time project.

My take

None of these individually would justify a dedicated project, but reviewing them together is a good prompt to audit your own pipelines: do you still have long-lived npm publish tokens sitting in repository secrets? Is secret scanning configured to block merges, or just to alert? Those two questions alone are worth an afternoon this month, regardless of what else is on the roadmap.
