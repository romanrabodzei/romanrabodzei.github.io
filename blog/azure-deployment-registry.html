Stop Asking Me "What's Deployed Where": Building an Azure Deployment Registry

Roman Rabodzei · July 2026 · ~8 min read
Azure FastAPI Cosmos DB Key Vault DevOps Security

Every platform team eventually hits the same wall: someone asks "wait, is version 3.2 actually live for that customer, or did we roll back?" and the honest answer involves opening three pipeline run histories, a spreadsheet nobody trusts, and a Slack thread from four months ago. Separately — and much more quietly — an App Registration credential expires somewhere in a tenant nobody's looked at recently, and a production integration falls over on a Tuesday morning with an error message that doesn't mention "expired secret" anywhere near the top.

This post is about the tool I built to make both of those problems boring: a small deployment registry that every pipeline reports to after every run, paired with a daily scan that watches App Registration secrets and certificates before they quietly expire. Names and identifiers below are all placeholders — the actual thing runs against real customer environments, which stay exactly where they are.

The shape of the thing

Two small web apps share one App Service Plan: a FastAPI backend that owns all the data, and a server-rendered web UI that acts as the human-facing layer over the API. Pipelines POST a deployment event after every run — success or failure — and a daily Azure Function scans App Registrations across tenants and posts what it finds. Everything lands in Cosmos DB Serverless, with signing keys and shared secrets pulled from Key Vault at runtime rather than baked into app settings.

The interesting part isn't any single piece — it's that pipeline events, scheduled scans, and human-facing operations all converge on the same API and data layer, while keeping their own authentication paths and trust boundaries.

Every pipeline gets its own key, and only its own key

Pipelines authenticate with a short-lived HMAC-signed JWT (5-minute expiry), signed with a named API key issued per integration and stored in Key Vault. The API doesn't require a key identifier in the token — it tries every currently active named key in turn until one verifies, which sounds inefficient until you realize it means onboarding a new pipeline is just "generate a key, drop it in a pipeline variable," with zero coordination needed on the token-signing side. 

signature = HMAC-SHA512(key=NAMED_API_KEY, msg=jwt_header_and_payload)
# API iterates active named keys from Key Vault until one verifies.
# No shared secret across integrations — deactivating one key
# doesn't touch anyone else's pipeline.

Each named key can be individually rotated or deactivated from the web UI without touching pipeline variables or redeploying anything — deactivation is a flag flip that takes effect on the next request, not a Key Vault operation that needs propagation time. A replay-protection cache (one entry per token, TTL matched to the token's own expiry) means a captured token is useless the second time it's presented, even inside its 5-minute window.

Deliberate non-goal: the admin login rate limiter is intentionally an in-memory, per-instance counter — not distributed across replicas or backed by a shared store. For a single-instance deployment that's a feature (no extra moving parts); it's explicitly documented as a limitation the day this needs to scale horizontally.

One event shape, several very different pipelines

Different pipeline families send slightly different field names for the same concept — one integration's "environment" comes from a deploy parameter called Environment, another's comes from a parameter called Subscription. Rather than forcing every team to agree on a shared schema up front (a fight nobody wins), the API accepts the source-specific shape and normalizes it on the way in.

Every deployment record gets a deterministic ID — a hash of customer, environment, source, product, and version — so re-posting the same event twice updates the same document instead of creating a duplicate. Whichever record is the newest for a given customer/environment/product combination gets flagged current; the previous one is demoted automatically in the same write. No cleanup job, no "which one is the real one" ambiguity.

The feature nobody asked for that turned out to matter most

The deployment tracking was the pitch. The part people actually thank me for is the credential expiry tracker. A daily function walks App Registrations across every connected tenant, reads out the secrets, certificates, and federated credentials attached to each one, and posts a snapshot to the same API. The dashboard surfaces a simple traffic light — active, expiring within 30 days, or already expired — and shows a dismissible banner the moment anything crosses into "expiring soon."

Federated credentials (the keyless, OIDC-based kind used by modern CI/CD) don't expire the same way certificates and secrets do, so they're tracked for visibility but deliberately excluded from the expiry countdown — showing a "days remaining" number that will never move would just be noise.

Locking down the login page

The admin login endpoint has a sliding-window rate limiter: five failed attempts from an IP within five minutes and that IP gets throttled with a 429 and a Retry-After header — including on a request with the correct key, because the limiter blocks by source, not by whether the credential was right. Client IP is read from the first hop of the forwarding header, which is safe specifically because the app only ever sits directly behind the platform's own front door — that assumption is written down explicitly so future-me doesn't get surprised if a CDN or gateway ever gets added in front of it.

  • Successful login clears that IP's counter; other IPs are never affected.
  • Session cookie is HttpOnly; Secure; SameSite=Strict, HMAC-signed, 8-hour TTL.
  • Every login attempt — success, failure, or rate-limited — emits a structured audit event with client IP, user agent, and timestamp. Never the credential itself.

Practical takeaways

The pattern that made this worth building: one write path, multiple trust levels. Pipelines, scheduled jobs, and human admins all end up at the same API and data layer, but cross the boundary with credentials scoped to their role. Deployment integrations can submit deployment events, monitoring integrations can submit monitoring data, while administrative operations stay behind a separate trust boundary.

If you're tracking anything across more than a couple of teams — deployments, credentials, compliance status, whatever — resist the urge to make everyone agree on one schema before you start. Let each source send what it naturally has, normalize centrally, and spend your actual design effort on the auth boundary instead. That's the part that's hard to retrofit later.
