Kubernetes v1.37 Workload-Aware Scheduling: Pod Resources, Resize Preemption, and Node Lifecycle

Roman Rabodzei · Oct 2026 · ~9 min read
Kubernetes v1.37 AKS Scheduling AI/ML Workloads Batch

Kubernetes v1.37 landed in September 2026, and the scheduling-related changes are the ones I've spent the most time digging into. Three features stand out for anyone running AI/ML or batch workloads on AKS: Pod-Level Resource Managers graduating to Beta, Scheduler Preemption for In-Place Pod Resize landing as Alpha, and the new Node Lifecycle Conditions API. None of these are flashy on their own, but together they're a meaningful step toward Kubernetes handling workload-aware scheduling the way GPU-bound and batch-heavy platforms actually need it to.

Pod-Level Resource Managers (Beta)

Building on Pod-Level Resources introduced in v1.35, this feature lets you define resource requests and limits at the pod level rather than summing them container-by-container. For pods with multiple containers that share a workload — a main process plus a metrics sidecar, or a training container with a data-loading helper — this means the scheduler can reason about total pod footprint directly instead of you having to carefully tune each container's individual limits to avoid over- or under-provisioning the pod as a whole.

On AKS, this matters most for GPU and memory-heavy AI/ML pods with sidecars, where getting per-container limits exactly right has always been fiddly and error-prone. Beta status means it's disabled by default but stable enough to pilot — I'd enable it on a non-production node pool running representative multi-container AI workloads before rolling it further.

Scheduler Preemption for In-Place Pod Resize (Alpha)

In-place pod resize itself reached General Availability in v1.35 — the ability to change a running pod's CPU/memory requests without restarting it. What v1.37 adds, in Alpha, is scheduler-level preemption support specifically for resize requests: when a pod asks to grow and there isn't currently room on its node, the scheduler can now evict lower-priority pods to make space for the resize, the same way it already does for new pod placement.

This closes a real gap. Before this, a resize request that couldn't be satisfied in place would simply fail or wait — there was no mechanism to make room for it. For workloads that scale their own resource footprint dynamically (autoscaling within a training job as batch size grows, for instance), this makes in-place resize a genuinely usable primitive rather than a best-effort one.

Caveat: this is Alpha — off by default, feature-gated, and not something I'd run in production yet. Worth testing in a dev cluster if your workloads already lean on in-place resize, so you understand the preemption behaviour before it matures.

Node Lifecycle Conditions

Kubernetes has always had scattered ways to describe node health — taints, readiness, provider-specific annotations — but no single, Kubernetes-owned convention for signalling that a node is in a particular lifecycle phase (draining, about to be replaced, degraded but not yet unschedulable). Node Lifecycle Conditions introduces a shared, structured way to express this, which matters a lot for schedulers, autoscalers, and operators that need to make placement or eviction decisions based on node state.

For AKS specifically, this is the kind of API that node-provisioning systems — cluster autoscaler, Node Auto Provisioning, and the new Flex Nodes preview — can build on to communicate more precisely with workload-aware schedulers and controllers, instead of every provider inventing its own signalling convention.

What this means for AI/ML platforms on AKS

  • Multi-container training pods get simpler, more accurate resource accounting once Pod-Level Resource Managers is enabled.
  • Dynamic workloads that resize themselves at runtime get a real path to being satisfied even under contention, once preemption for resize matures past Alpha.
  • Node provisioning systems gain a standard signal to build smarter scale-down and replacement logic on top of, which should make AKS's own autoscaling story more precise over time.

My take

None of these three features are ready to flip on in production today except Pod-Level Resource Managers for careful pilots. But the direction is clear: Kubernetes scheduling is being extended, feature by feature, to handle the resource patterns that AI/ML and batch workloads actually have — variable, multi-container, and dynamically resizing — rather than the static web-service shape the scheduler was originally designed around. Worth tracking closely if AKS is your AI platform's compute layer.
