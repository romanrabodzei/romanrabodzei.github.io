Copilot Code Reviews for Azure Repos: Effort Levels, Faster Resolves, and Audit Logging

Roman Rabodzei · Oct 2026 · ~4 min read
Azure DevOps GitHub Copilot Code Review DevOps Governance

Copilot Code Review for Azure Repos went to public preview in late August 2026, and since then Microsoft has shipped a steady stream of refinements rather than a single big follow-up release. Three of them are worth a closer look because they change how a team actually operates the feature day to day, rather than just what the review comments themselves look like.

Effort levels: controlling depth and cost

Every pull request review now has a configurable effort level — Lite or Balanced — that controls how much time Copilot spends on the review. This is a genuinely useful cost and noise control: a small, low-risk change doesn't need the same depth of review as a large or security-sensitive one, and running the deeper review on every PR regardless of size is pure waste. The default can be set at both the project level (project admins set a default for every repository underneath) and overridden per repository, which is the right granularity — a shared default with an escape hatch for the one repo that genuinely needs deeper review every time.

Resolving comments without a second pass

The before-state here was more annoying than it sounds: apply a suggested change, commit it, then go back through the PR and manually resolve each related comment one at a time. Now, applying and committing a suggested change from a Copilot review resolves the related comments in the same action. It's a small UX fix, but it removes a whole extra pass through the PR that existed for no reason other than the tool not connecting "I committed this suggestion" to "this comment is now resolved."

Audit log events: visibility for governance, not just usage

Copilot Code Review usage is billed per review to the subscription, which makes "where is this actually enabled, and who changed it" a real governance question once more than a couple of teams are using it. Azure DevOps audit logs now capture:

  • Enable/disable of Copilot Code Review at the organization, project, or repository level
  • Changes to the configured agent pool
  • Changes to custom instructions at the organization or project level
  • Changes to the default effort level at the project or repository level
  • Branch policies added for automatic code reviews at the project or repository level

That's enough to answer "who turned this on for this repo" and "who changed our custom instructions" after the fact, from the standard Auditing page, without needing a separate tracking mechanism bolted on by the platform team.

Practical note: if you're rolling Copilot Code Review out past a pilot team, set the effort-level default at the project level first, then only override per-repository where a team has an actual case for it — that keeps the audit trail meaningful instead of every repo drifting to its own setting by accident.

What's still missing

One open gap, raised directly in the post's comments: there's currently no plan to let Copilot propose a pull request directly from a tagged work item in Azure Boards, the way GitHub's coding agent can from a GitHub issue. Microsoft's answer is that this experience exists today only if you move your repositories to GitHub — worth knowing if that workflow is a deciding factor for your team, since it's not on the Azure Repos roadmap as a near-term fix.
