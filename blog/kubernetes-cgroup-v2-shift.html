The Shift to cgroup v2 in Kubernetes: What You Need to Know

Roman Rabodzei · Nov 2026 · ~6 min read
Kubernetes AKS Linux cgroups Resource Management

cgroup v2 has quietly become the default on most current Linux distributions, and Kubernetes' own newer memory-management features — Memory QoS graduating to Beta in v1.37 among them — now assume it. If your node images are still running cgroup v1, this is the point where "it still works" starts becoming "it's blocking features you actually want," and worth planning the migration deliberately rather than discovering it during an unrelated upgrade.

What actually changed

cgroup v1 organizes resource controllers (CPU, memory, block I/O) into separate, independently mountable hierarchies — a process can sit in different positions across the cpu hierarchy and the memory hierarchy simultaneously, which made consistent accounting and some classes of resource interaction genuinely hard to reason about. cgroup v2 replaces that with a single unified hierarchy: every controller for a given cgroup lives at the same place in one tree. That's not just tidier — it enables accounting and control features that don't have a clean v1 equivalent, including Pressure Stall Information (PSI) metrics for memory, CPU, and I/O contention, which several of Kubernetes' newer memory-management features depend on directly.

Why Kubernetes features increasingly require it

Memory QoS — which uses the memory controller to give the kernel better guidance on how to treat container memory under pressure — is built on cgroup v2's memory controller semantics and doesn't have a meaningful v1 equivalent. The same is true for a growing list of scheduling and eviction refinements: they're written against v2's accounting model because it's the one that actually gives the kubelet the signal fidelity these features need. Staying on v1 doesn't just mean missing out on one feature — it increasingly means falling behind on the whole direction resource management in Kubernetes is heading.

What to actually check before migrating

  • Container runtime version. containerd and CRI-O both need versions with solid cgroup v2 support — current releases on any supported Kubernetes version should be fine, but older pinned runtime versions are worth auditing explicitly.
  • Node OS image. On AKS and most managed Kubernetes offerings, the switch is really a node image version decision — current Ubuntu and Azure Linux node images default to cgroup v2 already, so for many clusters this has already silently happened at the last node image upgrade.
  • Custom monitoring or security agents reading cgroup paths directly. Anything that parses /sys/fs/cgroup/ paths assuming the v1 layout (separate per-controller mount points) needs updating for the unified v2 path structure — this is the most common thing that silently breaks.

How to check what you're actually running: cat /sys/fs/cgroup/cgroup.controllers on a node — if that file exists and lists controllers, you're on v2. Its absence (and a populated /sys/fs/cgroup/memory/ directory instead) means you're still on v1.

The migration itself is usually anticlimactic

For most workloads, the move to cgroup v2 is invisible — resource requests and limits are expressed the same way at the Kubernetes API level regardless of which cgroup version the kubelet translates them into underneath. The places it isn't invisible are exactly the ones above: anything reading raw cgroup paths, and any feature you've been waiting to enable that turns out to require v2. Worth checking both before your next node image rollout, rather than after.
