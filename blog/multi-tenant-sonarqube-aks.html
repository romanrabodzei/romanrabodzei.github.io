Cloning SonarQube Five Times Without Losing My Mind: A GitOps Story on AKS

Roman Rabodzei · July 2026 · ~9 min read
SonarQube AKS ArgoCD GitOps Azure Kubernetes DevOps

Somewhere around the third time a team lead asked "can we get our own SonarQube instance?" I realized I had two options: keep clicking "New Namespace" in the Azure portal until my mouse wore out, or actually build something that scales past copy-paste. This post is about the second option — running multiple SonarQube instances on a single AKS cluster, provisioned by Bicep and reconciled continuously by ArgoCD, so that "spin up instance number five" is a Git commit, not a Tuesday afternoon.

Fair warning: this post is about the architecture and the patterns, not any particular client's domain names, resource groups, or org charts — those are staying exactly where they belong, which is nowhere near the public internet.

The shape of the thing

At a high level: traffic hits an Application Gateway running in WAF mode, which is wired to the cluster's Ingress resources via AGIC (Application Gateway Ingress Controller) — so the moment you add an Ingress object, AGIC rewrites the Gateway's routing rules for you. No manual backend pool editing, which is good, because manually editing backend pools is how Fridays get ruined.

Inside the cluster, each SonarQube instance lives in its own namespace, with its own Helm release, its own Ingress, and its own slice of a shared PostgreSQL Flexible Server reachable only over a private endpoint. Nothing about SonarQube's data plane touches the public internet — the only public surface is the Gateway itself.

GitOps, or: how I stopped SSH-ing into things at 11pm

Every instance is deployed by ArgoCD using the app-of-apps pattern: a single root Application watches a folder in Git, and every app-<instance>.yaml file dropped into that folder automatically becomes its own ArgoCD Application — no manual argocd app create, no clicking through a UI five times and hoping you didn't fat-finger a namespace name on instance number four. 

k8s/argocd/
├── app-of-apps.yaml          # the root app — watches this folder
├── app-team-alpha.yaml
├── app-team-beta.yaml
├── app-team-gamma.yaml
└── app-team-delta.yaml       # copy, rename, done

k8s/helm/
├── team-alpha/
│   ├── chart-values.yaml     # image tag, JDBC settings, plugins
│   ├── namespace.yaml
│   ├── secret-provider-class.yaml
│   ├── ingress.yaml
│   └── network-policy.yaml
└── team-beta/ (same shape)

Adding a sixth instance is, genuinely, cp -r, sed a few names, git push, and go get coffee. ArgoCD polls every few minutes, notices the new Application, and reconciles namespace, secrets, ingress, and the Helm chart itself — in that order, automatically. The most technical part of "provisioning a new tenant" is now typing the team's name correctly.

selfHeal: true is doing a lot of quiet heroic work here. Somebody manually edits a ConfigMap in production because "it's just a quick fix"? ArgoCD notices the drift within a few minutes and politely reverts it back to whatever Git says reality should be. Git wins. Always.

Secrets that never touch a YAML file

Nobody wants database passwords sitting in a Git-tracked values.yaml, so this setup leans on the AKS Secrets Store CSI driver pointed at Azure Key Vault. Each namespace gets a SecretProviderClass that pulls the connection details from Key Vault and materializes them as a native Kubernetes Secret, which the Helm chart then consumes as environment variables to build the JDBC URL at pod startup. 

Key Vault ──[CSI driver]──► SecretProviderClass
                                  │
                       (auto-creates K8s Secret)
                                  │
                       postgres-host / username / password
                                  │
                       env vars → JDBC connection string

The kubelet's managed identity is the only thing with permission to read those secrets — no pod identity dance required, no developer laptop ever needs to know a production database password exists.

Cilium says "no" by default

Each namespace ships with a handful of CiliumNetworkPolicy resources: allow traffic within the namespace, allow the Application Gateway to reach the SonarQube pod on its port, and allow egress for the things SonarQube actually needs (the database, Key Vault, DNS, plugin downloads). The moment any policy targets a namespace, Cilium flips it to default-deny for that direction — so anything not explicitly listed simply doesn't happen. Which is exactly the kind of boring, predictable behavior you want from a security control.

One login to rule them all

Every instance is wired up to SAML SSO via Microsoft Entra ID, with Just-in-Time provisioning — group membership in Entra decides whether you land as an admin or a regular user in SonarQube, synced automatically on login. Nobody remembers a SonarQube-specific password because nobody has one. The default admin account still exists as a break-glass fallback, tucked safely away, changed from the factory default before it ever saw daylight (yes, I checked — twice).

Bonus round: making Copilot read the dashboards for me

The genuinely fun part: SonarQube ships an MCP (Model Context Protocol) server, which means GitHub Copilot in VS Code can query issues, quality gates, and metrics directly — no more alt-tabbing to a browser to check whether a PR broke the quality gate. You just ask: 

Show me all open critical and blocker issues in team-alpha's project.

…and Copilot calls the MCP tool, reads the live data, and hands back a table with file and line references. It's a small thing, but "AI reads my code quality dashboard so I don't have to context-switch" is exactly the kind of small thing that adds up to a genuinely better afternoon.

Practical takeaways

Multiplying SonarQube instances used to mean multiplying the manual work — a new App Registration, a new Ingress, a new set of copy-pasted YAML with one typo waiting to happen. Templating the Helm values, automating the ArgoCD Application registration, and pushing secrets through Key Vault instead of Git turned "provision a new tenant" from an afternoon into a five-minute PR.

If you're staring down a similar "everyone wants their own instance of X" problem: model the instance as data (a values file + an ArgoCD Application manifest), not as a one-off manual deployment. Future-you, at 11pm on a Friday, will send present-you a thank-you note.
